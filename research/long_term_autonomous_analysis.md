## 1. 현재 하네스 역량 평가

### 1.1 보유 역량

| 역량 | 구현 상태 | 구현 방식 |
|------|----------|----------|
| 작업 단위 자동 순환 | 완료 | `orchestrator.sh` — 상태 머신 기반 자동 세션 순환 |
| 정책 코드 수준 강제 | 완료 | `.claude/hooks/` — 5개 hook 스크립트 |
| 역할별 규칙 분리 | 완료 | `.claude/rules/` — 파일 접근 시 자동 로드 |
| 복구 체계 | 완료 | `rollback_last_good.sh`, `collect_status.sh`, Recovery Gate |
| 에이전트 역할 분리 | 완료 | planner/coder/reviewer/initializer 4-에이전트 |
| 계약 기반 작업 | 완료 | Sprint Contract — reviewer 사전 합의 |
| QA 튜닝 피드백 | 완료 | `state/qa_tuning_log.json` — 놓친 이슈 추적 |
| 하네스 진화 메커니즘 | 완료 | `docs/harness_assumptions.md` — 가정 추적/재검증 |
| 안전장치 | 완료 | max-sessions, max-hours, 연속실패 중단 |

### 1.2 현재 가능한 자율 운영 수준

```bash
# 잠자기 전에 실행
bash orchestrator.sh --max-sessions 20 --max-hours 4

# 아침에 결과 확인
cat claude-progress.txt
```

- 작업 선택 → 계약 검토 → 구현 → 검증 → 리뷰 **자동 순환**
- smoke 실패 시 **자동 복구 시도**
- 위험 명령 **자동 차단** (rm -rf, git push --force)
- 반려 시 **자동 재작업**
- 비용/시간 한계 도달 시 **자동 중단**

### 1.3 프로젝트 규모별 자율도

| 규모 | 자율도 | 사람 개입 |
|------|-------|----------|
| 작업 5개 이하 | 완전 자율 가능 | 결과만 확인 |
| 작업 10-20개 | 반자율 | 1일 1회 방향 확인 + progress 리뷰 |
| 작업 50개+ | 마일스톤 단위 | 마일스톤마다 아키텍처 검토 + 우선순위 재조정 |
| 6개월+ 장기 | 스프린트 단위 | 2주마다 하네스 감사 + feature_list 재구성 |

## 2. 현재 한계 분석

### 2.1 전략적 판단 부재

현재 오케스트레이터는 **전술적**(다음 작업 결정)이지 **전략적**(전체 방향 재평가)이지 않다.

- 10개 작업을 순서대로 처리하는 것은 가능
- 50개 작업 중간에 "이 접근이 틀렸다, 아키텍처를 바꾸자"라고 판단하는 것은 불가능
- 기술 부채가 축적되고 있는지 감지하지 못함
- 마일스톤 완료 후 다음 마일스톤의 작업을 자동으로 분해하지 못함

### 2.2 모호한 요구사항 처리 불가

- "사용자 경험을 개선하라" → 판단 불가
- "GET /todos에 pagination 추가" → 처리 가능
- feature_list.json에 **명확한 completion_criteria**가 있어야만 동작

### 2.3 외부 의존성 대응 불가

- API 키 만료, 서비스 장애, 라이브러리 breaking change
- 오케스트레이터는 3회 연속 실패 시 중단하지만, 원인을 진단해서 사람에게 알리지는 못함
- 보안 취약점이 발견되어도 자동 대응하지 못함

### 2.4 품질 천장

- reviewer가 놓치는 이슈 유형은 계속 놓침
- QA 튜닝 루프가 있지만 자동 적용이 아닌 수동 적용
- "작동하지만 설계가 나쁜" 코드를 걸러내는 능력에 한계

### 2.5 판단 한계 인식 부재

- 에이전트가 "내가 판단할 수 없는 문제"를 만났을 때, 무한 재시도하거나 잘못된 판단을 할 위험
- 사람에게 알리고 대기하는 메커니즘이 없음

## 3. 필요한 추가 계층

### 3.1 5계층 자율 운영 아키텍처

```
┌─────────────────────────────────────────┐
│ 5. 대시보드 계층 (모니터링)               │
│    비용, 품질, 진행률, 이슈 추이           │
├─────────────────────────────────────────┤
│ 4. 감시 계층 (외부 의존성)                │
│    API 상태, 라이브러리 변경, 인프라 건강    │
├─────────────────────────────────────────┤
│ 3. 에스컬레이션 계층 (판단 한계 인식)       │
│    "이건 사람이 결정해야 한다" 자동 판단     │
├─────────────────────────────────────────┤
│ 2. 전략 계층 (방향 재평가)                │
│    마일스톤 관리, 로드맵 재검토, 우선순위    │
├─────────────────────────────────────────┤
│ 1. 전술 계층 (현재 하네스) ✅              │
│    planner → contract → coder → reviewer │
└─────────────────────────────────────────┘
```

### 3.2 전략 계층 — Strategist Agent

**역할:**
- 마일스톤 단위 로드맵 관리 (`roadmap.json`)
- 마일스톤 완료 시 다음 마일스톤의 작업 자동 분해
- 진행 상황 기반 우선순위 재조정
- 기술 부채 축적 감지 → 리팩토링 작업 자동 삽입
- "이 접근이 틀렸다" 판단 → 방향 전환 제안

**트리거:**
- 마일스톤의 모든 작업 완료 시
- 연속 반려 5회 이상 시 (설계 문제 의심)
- known_issues가 임계치 초과 시
- 예정 대비 진행률 50% 미만 시

**산출물:**
- `roadmap.json` — 마일스톤 목록, 목표, 상태
- feature_list.json 자동 갱신 — 다음 마일스톤의 작업 추가
- `state/strategic_review.json` — 전략 재평가 기록

**동작 방식:**
```
마일스톤 N 완료
    │
    ├─ claude-progress.txt 전체 분석
    ├─ known_issues.json 분석
    ├─ 코드베이스 아키텍처 평가
    │
    ├─ 방향 유지? → 마일스톤 N+1 작업 분해 → feature_list.json 갱신
    ├─ 방향 수정? → 수정 제안 + 에스컬레이션
    └─ 기술 부채? → 리팩토링 작업 삽입
```

### 3.3 에스컬레이션 계층

**에스컬레이션 조건:**

| 조건 | 심각도 | 자동 행동 |
|------|-------|----------|
| 모호한 요구사항 발견 | 중간 | Slack 알림 + 오케스트레이터 일시 중지 |
| 아키텍처 수준 결정 필요 | 높음 | Slack 알림 + 대기 |
| 보안 민감 변경 | 높음 | 구현 차단 + 즉시 알림 |
| 비용이 예산 70% 도달 | 중간 | 알림 (계속 진행) |
| 비용이 예산 90% 도달 | 높음 | 오케스트레이터 중단 |
| 동일 작업 3회 연속 반려 | 높음 | 작업 blocked 처리 + 알림 |
| 외부 서비스 2시간+ 장애 | 높음 | 해당 작업 skip + 알림 |

**에스컬레이션 방법:**
- Slack/이메일 알림 (MCP 연동)
- `state/escalation_log.json`에 기록
- 오케스트레이터 일시 중지 (사람 응답 대기)
- 사람 응답 후 자동 재개

**필요 파일:**
- `state/escalation_log.json` — 에스컬레이션 이력
- `state/escalation_policy.json` — 조건별 행동 정의
- `.claude/hooks/escalation-check.sh` — 조건 감지 hook

### 3.4 외부 감시 계층 — Watchdog

**주기적 감시:**

| 감시 대상 | 주기 | 감지 시 행동 |
|----------|------|------------|
| 헬스체크 URL 응답 | 매 세션 시작 | smoke 실패 → recovery |
| 의존성 보안 취약점 | 1일 1회 | 긴급 패치 작업 자동 생성 |
| API 키 만료 임박 | 1일 1회 | 에스컬레이션 |
| 디스크/메모리 사용량 | 매 세션 시작 | 로그 정리 + 에스컬레이션 |
| git remote 동기화 | 매 세션 시작 | merge 작업 생성 또는 에스컬레이션 |
| 라이브러리 major 업데이트 | 1주 1회 | 호환성 검토 작업 생성 |

**필요 파일:**
- `scripts/watchdog.sh` — 주기적 감시 스크립트
- `state/watchdog_report.json` — 감시 결과
- 오케스트레이터 루프에 watchdog 호출 삽입

### 3.5 비용/품질 대시보드

**자동 추적 지표:**

| 지표 | 계산 방법 | 임계치 |
|------|----------|-------|
| 세션당 API 비용 | `--max-budget-usd` 로그 | 총 비용 > 예산 80% → 에스컬레이션 |
| 작업당 평균 세션 수 | progress 엔트리 카운트 | 작업당 > 8세션 → 작업 분할 필요 |
| 반려율 | rejected / total reviews | > 40% → strategist 재평가 요청 |
| 평균 작업 완료 시간 | 첫 세션 ~ 승인 시간 | 추세 악화 시 알림 |
| 미해결 known_issues | known_issues.json 카운트 | > 10개 → 정리 스프린트 자동 삽입 |
| QA 놓친 이슈 비율 | qa_tuning_log.json | > 20% → QA 튜닝 세션 트리거 |

**필요 파일:**
- `scripts/generate_dashboard.sh` — 대시보드 데이터 생성
- `state/dashboard.json` — 추적 지표 저장
- 오케스트레이터 종료 시 자동 생성

## 4. 구현 로드맵

### 4.1 도입 순서

| 순서 | 추가 계층 | 난이도 | 효과 | 소요 추정 |
|------|---------|-------|------|----------|
| 1 | 에스컬레이션 | 낮음 | "멈춰야 할 때 멈추는" 능력 | 1-2 세션 |
| 2 | 대시보드 | 낮음 | 진행 상황 가시성 | 1-2 세션 |
| 3 | 전략 계층 | 중간 | 마일스톤 자동 분해, 50개+ 작업 | 3-5 세션 |
| 4 | 외부 감시 | 중간 | 프로덕션 환경 안정성 | 2-3 세션 |

### 4.2 단계별 자율 운영 수준

| 단계 | 보유 계층 | 자율 운영 수준 | 사람 개입 |
|------|---------|-------------|----------|
| 현재 | 전술 | 작업 5-10개 자동 처리 | 매일 확인 |
| +에스컬레이션+대시보드 | 전술+안전 | 작업 20개, 위험 시 자동 알림 | 주 2-3회 확인 |
| +전략 계층 | 전술+전략+안전 | 마일스톤 단위 50개+ 작업 | 주 1회 방향 승인 |
| +외부 감시 | 전체 | 장기 프로덕션 운영 | 에스컬레이션 시에만 |

### 4.3 최종 자율 운영 플로우

```
사람: 프로젝트 목표 + 마일스톤 초안 작성 (1회)
  │
  ▼
Strategist: 마일스톤 1 작업 분해 → feature_list.json
  │
  ▼
Orchestrator: 자동 순환 (planner → contract → coder → reviewer)
  │                                    │
  ├─ Watchdog: 주기적 감시              ├─ 에스컬레이션 발생 시
  │   └─ 이상 감지 → 작업 생성 또는 알림  │   └─ Slack 알림 → 사람 응답 → 재개
  │                                    │
  ├─ Dashboard: 매 세션 지표 갱신        │
  │                                    │
  ├─ 마일스톤 1 완료                     │
  │   └─ Strategist: 진행 평가          │
  │       ├─ 방향 유지 → 마일스톤 2 분해  │
  │       └─ 방향 수정 → 에스컬레이션     │
  │                                    │
  └─ 반복                               │
                                       │
사람: 에스컬레이션 응답 + 주 1회 대시보드 확인
```

## 5. 기술적 구현 방안

### 5.1 Strategist Agent 구현

```
.claude/agents/strategist.md  — 에이전트 정의
roadmap.json                  — 마일스톤 로드맵
state/strategic_review.json   — 전략 재평가 기록
```

오케스트레이터에 전략 세션 트리거 추가:
```bash
# orchestrator.sh에 추가
if [ "$(has_remaining_work)" = "false" ]; then
  # 현재 마일스톤 완료 → strategist 호출
  run_agent "strategist" "마일스톤 완료. roadmap.json을 읽고 다음 마일스톤의 작업을 분해하세요."
fi
```

### 5.2 에스컬레이션 구현

```
.claude/hooks/escalation-check.sh  — 조건 감지
state/escalation_log.json          — 이력
state/escalation_policy.json       — 정책
```

오케스트레이터에 에스컬레이션 체크 삽입:
```bash
# 매 루프마다 에스컬레이션 조건 확인
check_escalation() {
  # 연속 실패 확인
  # 비용 확인
  # known_issues 임계치 확인
  # 결과에 따라 Slack 알림 또는 중단
}
```

### 5.3 Watchdog 구현

```
scripts/watchdog.sh              — 감시 스크립트
state/watchdog_report.json       — 감시 결과
```

오케스트레이터 루프 시작 시 watchdog 호출:
```bash
# 매 N번째 세션마다 watchdog 실행
if [ $((SESSION_COUNT % 5)) -eq 0 ]; then
  bash scripts/watchdog.sh
fi
```

### 5.4 대시보드 구현

```
scripts/generate_dashboard.sh    — 대시보드 생성
state/dashboard.json             — 지표 저장
```

오케스트레이터 종료 시 자동 생성:
```bash
# 오케스트레이터 종료 시
bash scripts/generate_dashboard.sh
```

## 6. Agent Teams 활용 가능성

Claude Code의 Agent Teams 기능을 활용하면 오케스트레이터를 대체할 수 있다:

| 현재 방식 | Agent Teams 방식 |
|----------|----------------|
| orchestrator.sh가 순차 호출 | Planner가 Team Lead, Coder/Reviewer가 Teammate |
| 파일 기반 소통만 가능 | 팀원 간 직접 메시징 가능 |
| 순차 실행 (planner → coder → reviewer) | 병렬 실행 (coder 구현 중 reviewer가 이전 작업 검토) |
| 에이전트 전환 시 컨텍스트 리셋 | 각 팀원이 독립 컨텍스트 유지 |

단, Agent Teams는 실험적 기능(`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`)이며, 세션 간 상태 유지는 여전히 하네스 파일에 의존해야 한다.

## 7. 리스크 및 고려사항

### 7.1 비용

| 운영 방식 | 예상 비용 (작업당) |
|----------|-----------------|
| 현재 (순차 4세션) | $5-20 |
| +전략 세션 | $5-25 |
| Agent Teams (병렬) | $15-50 (3개 인스턴스 동시) |

### 7.2 품질 수렴 한계

- 자율 운영이 길어지면 에이전트의 판단 패턴이 수렴하여 동일 유형의 실수를 반복할 수 있음
- 하네스 감사(harness_assumptions.md) + QA 튜닝 세션이 이를 방어하지만, 완벽하지 않음
- **주기적 사람 검토가 장기적으로 필수**

### 7.3 복잡도 증가

- 추가 계층마다 상태 파일, 스크립트, 정책이 증가
- 디버깅 난이도 증가
- 단순 프로젝트에는 과잉 엔지니어링

### 7.4 권장 적용 범위

| 프로젝트 규모 | 권장 계층 |
|-------------|---------|
| 개인 사이드 프로젝트 | 전술 계층만 (현재 하네스) |
| 중규모 팀 프로젝트 | +에스컬레이션 + 대시보드 |
| 대규모 장기 프로젝트 | 전체 5계층 |

---

## 8. 결론

현재 하네스는 **명확한 작업 목록이 있는 10-20개 작업을 자율 처리**할 수 있다. 에스컬레이션과 대시보드를 추가하면 **사람이 주 2-3회만 확인하는 반자율 운영**이 가능하다. 전략 계층까지 추가하면 **마일스톤 단위 자동 진행**으로 50개+ 작업 프로젝트를 처리할 수 있다.

완전한 자율 운영(사람 개입 0)은 현재 모델 능력으로는 **불가능하며 바람직하지도 않다**. Anthropic의 하네스 설계 원칙이 강조하듯, "하네스의 모든 컴포넌트는 모델이 못하는 것에 대한 가정을 인코딩"하며, 전략적 판단과 에스컬레이션 대응은 여전히 사람의 영역이다.

목표는 **"사람의 개입 빈도를 최소화하되, 필요할 때 정확히 알리는"** 시스템이다.
